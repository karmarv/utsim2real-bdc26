## 1. How this folder works

| Rule | Description |
|---|---|
| When to write a record | A version becomes decision-ready for submission (it passed the upload gate, or a gate result changes the plan), or a rule, data-use, legal or organizer question is decided. Diagnostics, ablations and per-class tables stay in the model READMEs. |
| File name | `YYYY-MM-DD-<scope>-<topic>.md`. Scope: the strategy code in lowercase (`s1`, `s2`, ...; a variant keeps its parent code, for example `s1-closeout-...` for S1+C1), `rules` (data use, integrity, legal, organizer answers) or `plan`. |
| Size | About 40 lines at most: version, numbers, gate, decision. Long evidence is linked, not copied. |
| Template | Version, Context, Evidence, Gate, Decision, Outcome, Consequences, and for a packaged version Reproduce (below). |
| Reproduce | Written before the upload from `python common/tools/reproduce_submission.py <model> --tag <tag> --write-script --markdown`: every member's weights (path, md5), TTA and post-processing file, and the two commands (quick re-merge check; full test-frame inference with those weights, `test/reproduce_<tag>.sh`). Indexed in Section 6.1. |
| Updates | The leaderboard outcome and later facts are added to the same record. A replaced record gets a first line `Superseded by <record>` and stays. |
| Index | Every record has one row in Section 6; every upload and every decision-ready version has one row in Section 2. |

```
# <date> <strategy or scope>: <decision in a few words>
**Version.** model folder and submissions/<date>_<tag>/ (strategy code)
**Context.** what was being decided and why now (one paragraph)
**Evidence.** realval-A/B per class with bootstrap intervals, R, estimate, kit-scorer check (a table)
**Gate.** which gate of Section 3, the numbers against its thresholds, passed or failed
**Decision.** what we do
**Outcome.** CodaBench id, leaderboard numbers, confirmation passed or failed (added after the upload)
**Consequences.** what changes for later strategies, configs or rules
**Reproduce (weights and test run).** member table (weights path, md5, TTA, post-processing) and the commands
```

### 6.1 Reproducing a submission

Every scored version can be rebuilt from its checkpoints: its decision record has a **Reproduce** section (members, weight paths with md5, TTA, post-processing files, commands), and its model folder a generated `test/reproduce_<tag>.sh` (test-frame inference with those weights, merge, comparison with the scored zip, repackaging of the same 50 frames, official kit check). `python common/tools/reproduce_submission.py <model> --tag <tag>` re-merges the saved member predictions and checks them against the scored zip in a few seconds (all versions below: identical, 2026-10-15); S1 LUMPI re-run from its checkpoints gave identical boxes and frames. On an idle GPU a full re-run is bit-identical (IDENTICAL; on 2026-10-16 all seven V2X R5 members, Voxel R-CNN and PV-RCNN++ included, reproduced with a maximum difference of 0.0); a run sharing its GPU with training differed in the last digits (median 1e-5) and is reported as EQUIVALENT by a per-frame box matching. Checkpoints are not in git (`train/output/` is ignored): keep the folders listed in the records, or archive them with the release. The Release column names the first tag that holds the version's files; from 6.0 on that release also carries its checkpoints and zip as assets (`releases/<tag>/weights.json`; the tag map: [`RELEASES.md`](../../RELEASES.md#release-map-tags-leaderboard-submissions-weights)).
